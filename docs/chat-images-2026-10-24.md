Contracts agreed for this implementation:

- Existing authenticated attachment upload returns the shared `ChatAttachment` metadata (`id`, `name`, `content_type`, `size`). PNG/JPEG validation, byte/pixel limits, ownership, quota and private R2 storage precede success. Upload does not call an AI provider. Image `extracted_text` may be empty under the existing schema.
- Sending `attachment_ids` with the question resolves only owned images in that conversation. Analyse actual image pixels against that question, preserve orientation, strip metadata from provider payloads, retain unreadable/uncertain labels as uncertainty, and record the resulting context with the user turn. Do not claim a generic upload description answers every subsequent visual question.
- `vision_analyze` accepts an `attachment_id` and optional question, never arbitrary URLs, raw storage keys or model-supplied base64. Backend account, university and conversation scope remain authoritative.
- Authenticated `GET /api/v1/ai/chat/sessions/{session_id}/attachments/{attachment_id}/preview?size=thumbnail|large` returns a 384px or 1536px PNG with `private, no-store`; default is `thumbnail`. The public metadata DTO stays unchanged; clients construct this API route and use session authentication. Preview blob URLs are memory-only and released on account/component changes, or on viewer close for the large variant.
- SSE retains the existing `analysing_image` progress code and retryable error contract. Provider failure must not fabricate visual findings or silently continue without the image. External image links are not fetched by the vision resolver. Provider privacy gates and total deadlines apply.

Acceptance: own versus foreign/session/tenant image access; no inference on upload; original question reaches vision at send; malformed/decompression/oversized payload rejection; bounded privacy-respecting provider fallback; cache account/tenant/question isolation; authenticated previews; desktop/mobile attachment preview and clear upload/analysis failures; applicable API, TypeScript/lint and browser checks.

Implementation:

- `chat_images.py` resolves the exact private namespace after an owner/session/university lookup; PNG/JPEG is limited to 10 MB and 16 megapixels. Provider pixels preserve EXIF orientation, flatten transparency on white, remove metadata and fit within 3072px. Thumbnail pixels fit within 384px; the lazily fetched viewer variant fits within 1536px. Neither model inputs nor preview URLs enter client storage.
- At Send, image observations become explicit attachment context for the current question. Image turns skip speculative initial course retrieval; enabled tools can still retrieve material when needed. Follow-up tool calls resolve owned attachment IDs with backend session context. Analysis failure ends the turn with a retryable error, without a fabricated answer.
- Vision attempts Google, then eligible Groq, then eligible OpenRouter within 10s per tier / 25s overall. Google uses one SDK attempt. The 128-entry, one-hour analysis cache includes tenant, account, question and image hash, and rechecks provider eligibility. Production failures never use the development fixture response.
- Composer/message attachments now use assistant-ui's native iterators and attachment primitives with styling adapted from its [attachment element](https://github.com/assistant-ui/assistant-ui/blob/main/packages/ui/src/components/react/assistant-ui/elements/attachment.aui.tsx); attribution is retained in `assistant-ui.LICENSE`. Local image tiles open a preview dialog; sent image tiles use the authenticated API, including after history reload. Document tiles retain names, pending files can be removed, and upload/preview failures have recovery controls. Message actions use tooltip-wrapped ghost buttons with current palette tokens. Original compact input geometry and inline branch controls remain.
