## Evidence and remaining access

The deployed web bundle points to the expected staging API and Supabase project. The repaired public Supabase key returns 200 with Google enabled. Two independent rounds of public API liveness, infrastructure, anonymous `/auth/me` and CORS preflight probes each timed out after 25 seconds. These probes cannot establish a specific Render startup, database or CORS failure. Render runtime logs/access are required; neither a Render connector nor a configured API credential is available. Logs have been requested from the user.

Local API liveness returned 200 in 0.31s and infrastructure health returned 200 in 3.02s with database, Redis and storage healthy. Earlier local database connection failures remain historical evidence, not proof of a current database defect. No user authorization code, access token or account record was replayed/read for these probes.

After the user supplied Render startup logs, the API became reachable: liveness/infrastructure returned 200 and the unauthenticated profile route correctly returned 401. The deployed origin's OPTIONS request returned **400 Disallowed CORS origin**, and GET responses omitted `Access-Control-Allow-Origin`. This confirms browser access was blocked before profile verification. Add the exact web origin to Render's `ALLOWED_ORIGINS`, preserving other configured origins, and redeploy. The code default now also permits that origin, while unrelated Vercel origins remain rejected.

The supplied logs separately show two Uvicorn processes downloading/unpacking the same FlashRank `/tmp` files concurrently, resulting in invalid ONNX protobuf/missing ZIP errors followed by false `flashrank_prewarmed` messages. Use one async API process for the free pilot, package/validate the small model during Docker build and load that read-only cache at runtime. Local writable model caches are isolated per reranker instance and initialization is thread-locked; cold initialization stays off the event loop and startup warming is bounded/non-fatal. Log prewarm success only for an actual model. A container CI smoke loads the packaged model as the runtime user with download access blocked. This fixes a startup/reranker defect; it does not establish that the model race was the cause of a particular user's profile rejection.

The scheduled availability workflow also lacked both required repository URL variables, so its latest scheduled run failed before making a request. Configured only the public `STAGING_API_HEALTH_URL` (`/health/ready`) and `STAGING_WEB_URL` values and dispatched [a verification run](https://github.com/PansGPT/pansgpt/actions/runs/40209607400). No infrastructure credentials were uploaded. This repairs configuration for the existing ten-minute schedule; it does not guarantee uninterrupted free-tier availability.

## Contract and acceptance criteria (before implementation)

- Add `AuthProfileResponse` to `packages/types`, matching the existing Pydantic `/api/v1/auth/me` response: id, email, role, roles, nullable university/name/level/terms fields, is_onboarded, client_type and dev_bypass. Remove unsupported frontend-only `is_active`/university_name assumptions. Deleted-account rejection remains backend-authoritative.
- Session state and profile verification are distinct. Auth-event callbacks update session state synchronously; profile HTTP work runs outside the callback. Initial session restoration is bounded and may be retried by reloading sign-in state.
- Profile requests have a 15-second deadline, explicit cancellation and one in-flight request per identity/token. Token/account changes, logout and unmount invalidate pending work; late results cannot restore an obsolete profile. No local-storage profile, JWT metadata or cached role grants access after failure.
- Distinguish connection failure, deadline, service unavailable, expired/rejected session, forbidden access and malformed/mismatched profile responses. Present retryable service errors as connection/service problems rather than an invalid account. Keep live workspace integration blocked until an owned response validates.
- Preserve existing onboarding completion, logout, auth routes and retry controls. Render downtime is not fixed by suppressing verification. Explicitly allow the user-selected deployed web origin in the API's default CORS allowlist; do not allow arbitrary Vercel domains. Actual hosted CORS behavior still requires a reachable API.
- Verify cancellation, deduplication, stale-response isolation, status distinctions and owned response validation, plus the existing real disposable auth/shell journeys. Hosted user login remains open until the API is reachable and the journey succeeds.

No schema migration, data rewrite, role-cache authorization fallback or auth bypass is authorized by this change.
