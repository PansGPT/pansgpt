# Chat recovery — 14 November 2026

User-approved scope: simple response failure copy, bounded exponential backoff, honest waiting feedback and recovery appropriate to response, network, access, usage, upload, voice, history and generated-file failures. Continue `feature/pdf-study-workspace`.

## Contracts and acceptance

Later user correction: **remove the canned no-material answer entirely**. A successful search with no relevant excerpts continues to the answering model, which may use established academic knowledge and appropriate tools. An open PDF/course or attachment no longer bypasses semantic intent decisions: the router receives context-availability flags and distinguishes self-contained questions from requests to read unseen material. Document ownership/tool retrieval targets remain backend-scoped. Actual database/search outages remain retryable failures, never evidence absence. Remove prompts requiring a missing-material refusal; never invent document support or current facts. Automatic web fallback is disabled in the chat course lookup; explicit web decisions/tools keep existing permissions/privacy gates.

- Add `recovery` SSE frames `{state:"retrying", attempt:1..3, retry_after_ms:0..30000}`. These are system recovery notices, separate from model-authored public progress. Preserve optional error code/retryability in the client message state; display controlled public copy rather than raw transport/provider errors.
- Add optional `retry_message_id` to the stream request. It identifies an owned user question in the same session; reuse its stored text, parent and attachments. Edit/regenerate/retry are mutually exclusive. A retry cannot replay a question whose tool execution started, or create a second successful answer for an already answered question. No schema change: record a conservative retry block in the existing question metadata before tool execution is forwarded.
- Automatic retries stay inside an existing backend run/credit reservation for safe retrieval/image/search operations and before provider output/tool execution. Use at most three attempts with exponential backoff and jitter; respect retry-after hints and overall deadlines. Never retry validation, authorization, policy or exhausted quota errors. Never replay a whole stream POST automatically.
- A bare provider 429 fails over rather than repeatedly consuming an exhausted quota. Retry the same rate-limited operation only with an explicit cooldown within the 30-second wait cap and existing operation deadline. Provider creation retries remain inside the first-chunk budget; routing retries stay inside their attempt/total budgets.
- Safe browser GETs retry twice with backoff and bounded request deadlines; preserve existing data and manual recovery. Mutations/uploads do not replay automatically. Transcription may retry the same in-memory recording because it creates no message/file artifact.
- Show “This is taking longer than usual.” during a real wait, and “Trying again…” only during an actual retry. Stop/navigation/account change cancels pending work and timers. Offline status explains the required connection without claiming recovery succeeded.
- Failed responses offer Retry when safe, including empty answers. Reconcile saved history first: restore an already saved answer without another generation/charge; otherwise retry the existing owned question. Ambiguous pre-init network failures require reopening the chat rather than replaying an unidentifiable request. Preserve selected document, original action and attachment scope. Preserve existing composer drafts.
- Keep partial response text through terminal failures and empty done frames. Access/credit/quota/file validation failures retain actionable explanations. Upload failures retain the local file and expose retry; previews/downloads remain independent of generation.
- Upload retry prepares the retained local file for the next explicit Send; it never silently submits an unfinished question. Transcription retries retain at most the current bounded recording in memory and append recovered text to an existing draft. Offline sending is disabled and reconnecting never automatically sends the draft. A final `done` frame ends reading immediately rather than waiting indefinitely for socket EOF.
- Required verification: retry limits/delays/cancellation/no unsafe POST replay, owned retry authorization and tool/success guards, partial content retention, normal/study/mobile response UI, history/download/upload/voice recovery, strict types/lint/API checks and production build. Hosted/provider/native gates remain open.

## Later notice layout correction

User-approved presentation: match the supplied compact rounded warning card with an amber icon and close button. Place offline, local attachment-validation, transcription and conversation-action notices **above the composer**, outside its grid. Apply the same shared card style to failed responses and real retry/slow-response feedback. Keep response-specific failures beside the relevant response, and file-specific failures on their attachment. Try again.” and “Up to 4 files per message.” Desktop keeps fuller explanations. This changes presentation only; backend retry, permissions, credit and streaming contracts remain unchanged.
