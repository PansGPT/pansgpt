## Contracts before integration

Shared DTOs belong in `packages/types/src/settings.ts`; strict Pydantic models mirror them. All endpoints require the existing verified identity and server-held client key through a fixed same-origin Next proxy; responses are private/no-store.

- `PUT /api/v1/settings/password`: `{password,current_password?,nonce?}` → `{status:"updated"}`. FastAPI forwards the captured authenticated bearer to the configured Supabase Auth `/user`, with the public API key, never administrator authority. No password/token logging, persistence or automatic write retry. Return typed codes for weak/same password, required current password or reauthentication, invalid confirmation, rate limiting, expired identity and transient failure. Never close the form or show success before the provider confirms. Account switches must discard drafts and late responses.
- `POST /api/v1/settings/password/reauthenticate`: send the provider's confirmation code to the account's configured channel; show the code field only when needed. This does not grant a new session or bypass Supabase password-security policy.

  Provider adapter detail: this application endpoint is POST, but the upstream call is **GET** `/auth/v1/reauthenticate`, matching [GoTrue's actual router](https://github.com/supabase/auth/blob/master/internal/api/api.go) and [auth-js](https://github.com/supabase/auth-js/blob/master/src/GoTrueClient.ts). The upstream OpenAPI document currently labels that operation POST; the implementation takes precedence. The provider contract test verifies GET with no body. Password updates remain PUT `/auth/v1/user` and current-password mismatch gets an actionable, fixed message.

- `GET /api/v1/settings/sessions`: owned Supabase Auth sessions only, bounded to 100 plus a `has_more` flag. Return `{id,device,device_type,ip_address,created_at,last_active_at,is_current}`; current session is determined from the verified JWT `session_id`. No fabricated location, activity or device records. Missing metadata is explicitly unknown. No refresh tokens, secrets or session cryptographic material are serialized.
- `DELETE /api/v1/settings/sessions/{id}` and `DELETE /api/v1/settings/sessions`: end one owned non-current session or all other sessions, respectively, retaining the current session. Transactional owner/current-session checks precede deletion of Auth session rows; Supabase's existing refresh-token foreign key cascades. No Auth schema/grant changes. Missing/foreign/current targets fail safely. Actual Supabase session IDs are provider-managed UUIDs, not application-created IDs. API identity checks reject a revoked `session_id` on later requests; already-issued access tokens used directly against other services remain subject to their expiry and policies.
- `POST /api/v1/settings/feedback`: `{request_id,category,description}` → `{id,status:"received"}` after a committed support ticket and first reply. Category is existing `bug|account|content|billing|other`; description is bounded plain text. A client-created RFC 9562 UUIDv7 request ID is the ticket ID/idempotency key, not an ownership claim. Owner and any tenant are derived server-side. Retries reuse the key and cannot overwrite someone else's ticket or silently accept changed content. Existing support tables/RLS remain; no diagnostics, screenshots, IPs or conversation text are automatically attached.

No new database schema is required. Verify existing Auth/table SQL and ownership against a disposable database before connecting live UI. Use current base-schema fields so feedback does not depend on activation of administrative governance. Anonymous requests and unavailable infrastructure must never receive fake success. Feedback is available in staff triage through existing support records; outbound messages/email are not part of this batch.
