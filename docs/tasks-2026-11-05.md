## 1. Make task saves and error recovery reliable

**Priority:** High. **Status:** Implemented and locally verified; GitHub CI required before merge.

Current task mutations can overlap. Successful responses replace whole task objects, while failed edits or deletions restore a snapshot of the entire list. An older response or failure can therefore overwrite newer UI state.

- [x] Coordinate writes per task, or use mutation versions so stale responses cannot replace newer state.
- [x] Roll back only the affected mutation; preserve successful changes to other tasks and fields.
- [x] Use the server response for authoritative completion state and `completed_at`.
- [x] Restore both completion state and its timestamp when a completion request fails.
- [x] Make retry actions use the intended operation and current state.
- [x] Verify rapid edits, responses arriving out of order, completion toggles, and a failed edit/delete alongside another successful change.

**Acceptance:** The task list and details agree with persisted state after concurrent actions, failures and retries. Reloading does not reveal a successful edit that the UI incorrectly rolled back.

**Primary files:** [tasks-modal-view.tsx](../apps/web/components/shell/tasks-modal-view.tsx), [academic.ts](../apps/web/lib/academic.ts).

## 2. Keep unfinished tasks accessible as the list grows

**Priority:** High. **Status:** Implemented and locally verified; GitHub CI required before merge.

The planner requests completed and unfinished tasks together. The API defaults to 200 rows, ordered by descending due date, and the screen has no pagination. Completed or future-dated tasks can displace overdue or undated unfinished tasks.

- [x] Agree and record a bounded paging contract and ordering for active/completed tasks.
- [x] Align shared TypeScript DTOs, Pydantic contracts and client validation before integrating the change.
- [x] Keep overdue, upcoming and undated unfinished tasks accessible independently of completed history.
- [x] Add pagination or an equivalent explicit way to retrieve additional tasks, including loading, empty, error and retry states.
- [x] Verify more than 200 mixed tasks, equal due dates, undated tasks, and moving tasks between active and completed lists.

**Acceptance:** Every task can be reached without duplicates or unexplained omissions, while each API request remains bounded and owner/university scoped.

**Primary files:** [academic.py](../apps/api/app/routers/academic.py), [academic.ts contracts](../packages/types/src/academic.ts), [academic.ts client](../apps/web/lib/academic.ts), [tasks-modal-view.tsx](../apps/web/components/shell/tasks-modal-view.tsx).

**Implementation contract recorded before UI integration:** Add owner/university-scoped `GET /api/v1/tasks/page?state=active|completed&offset=0&limit=100`, returning `{ items: StudentTaskDto[], next_offset: number | null }`. Page size is 1?200; offsets are nonnegative and bounded to 1,000,000. Active pages order by due date/time (nulls last), then creation time and ID; completed pages order by completion time and ID. Preserve the existing array response from `GET /tasks` for compatibility. Add `GET /tasks/{task_id}` returning the existing `StudentTaskDto` with owner/university checks, so saved detail links work outside the first page. Load active and completed pages independently, expose explicit load-more/retry controls, and reset paging after mutations to avoid shifting offsets.
